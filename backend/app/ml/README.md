# LSTM 실험과 저장 모델 사용

API는 학습하지 않습니다. 별도 명령이 학습·평가·저장을 수행하고, 예측 API는 활성화된
버전의 모델과 스케일러를 로드해 재사용합니다. 활성 모델이 없으면 `weighted_average`
예측을 반환하며, 이때 LSTM 평가 점수는 반환하지 않습니다.

## 데이터 분리

분리 기준은 입력 기록의 연도가 아니라 **예측 정답의 시즌 연도**입니다.
기본값은 사용 가능한 예측 대상 연도 중 마지막을 테스트, 그 직전 연도를 검증으로
사용하고, 검증 연도보다 이전 사례만 학습합니다.

예를 들어 `--through-season 2025 --validation-season 2024 --test-season 2025`이면:

| 구간 | 예측 대상 시즌 | 사용 목적 |
| --- | --- | --- |
| 학습 | 2023년 이하 | 가중치 및 스케일러 학습 |
| 검증 | 2024년 | 조기 종료, 최적 epoch 선택 |
| 테스트 | 2025년 | 학습 종료 후 MAE·RMSE 계산 |

2025년 테스트 입력에 2022~2024년 기록이 포함되는 것은 정상입니다. 2025년을
예측할 때 이미 알 수 있는 정보이기 때문입니다. 2025년 정답은 가중치 학습이나
조기 종료, 스케일러 `fit`에 사용하지 않습니다. 검증/테스트 값이 학습 범위를 넘으면
정규화 결과가 0~1을 벗어날 수 있으며 이를 강제로 잘라내지 않습니다.

학습과 API 예측은 `season_features.py`의 동일한 전처리를 사용합니다. 선수·연도별로
팀별 누적 기록을 먼저 합산하고, 타율·출루율·장타율·wOBA·ERA·WHIP 등을 다시 계산합니다.
비율 지표를 단순 평균하지 않으며, 최소 PA·등판 수 조건도 합산 후 적용합니다.

연속된 4개 연도(입력 3개+정답 1개)가 필요한 학습 창만 사용합니다. 누락 연도,
합산 후에도 남은 중복 연도, 결측·비정상 지표가 포함된 창은 제외하고 제외 수를 저장합니다.
API도 최신 3개 시즌에 같은 검사를 적용합니다. 최신 기록에 문제가 있으면 더 오래된
구간으로 바꿔 예측하지 않고, 유효한 최근 연속 3시즌 기록이 필요하다는 응답을 반환합니다.
모든 구간에 데이터가 없으면 오류를 내며 학습 데이터의 오차로 대신 평가하지 않습니다.

투수 입력은 `ERA, WHIP, K/9, BB/9, HR/9, IP, IP/G, GS/G` 8개입니다.
출력은 `ERA, WHIP, K/9`입니다. 투구 이닝은 아웃 수로 변환해 합산합니다.
`54 2/3`과 야구식 `54.2`는 모두 164아웃으로 처리하며, 54.2 십진 이닝으로 계산하지 않습니다.
`K/9=SO×27/아웃 수`, `BB/9=BB×27/아웃 수`, `HR/9=HR×27/아웃 수`로 계산하므로
원본의 비율 컬럼이 비어 있어도 누적 기록이 유효하면 사용할 수 있습니다.
누적 기록이 없거나 투구 아웃 수가 0이면 0으로 대체하지 않고 해당 시즌을 제외합니다.

예측 기준 시즌 API는 추가하지 않았고 최신 기록을 사용합니다. 기존 신뢰도 배지와
기록 수 기반 high/medium/low 규칙은 유지합니다.

연도별 확장 검증(rolling origin)은 검증/테스트 연도를 바꿔 여러 번 실행하면 됩니다.
예: `학습≤2021/검증2022/테스트2023`, `학습≤2022/검증2023/테스트2024`.
하이퍼파라미터는 검증 점수로 선택하고, 최종 테스트 점수로 반복 튜닝하지 마세요.
같은 선수의 과거가 학습과 이후 연도 평가에 함께 존재하는 것은 기존 선수의 미래 예측
목표에 맞습니다. 처음 보는 선수에게의 일반화가 목적이면 별도의 선수 단위 분리도 필요합니다.

기본 `--through-season`은 전년도입니다. 진행 중 시즌의 부분 기록과 완료 시즌을
섞지 않기 위한 기본값이며, 완료 데이터가 확인된 경우 명시적으로 바꿀 수 있습니다.

## 실행

PostgreSQL과 연결 가능한 backend 환경에서 실행합니다. Docker를 사용한다면
저장소 루트에서 아래 명령의 앞부분을 `docker compose exec backend`로 시작합니다.
컨테이너의 `/app`은 호스트 `backend`와 연결되어 저장 모델도 유지됩니다.

빠른 동작 확인(선수 30명, 최대 3 epoch). 저장만 하며 서비스 모델은 바꾸지 않습니다:

```sh
docker compose exec backend python -m app.ml.train --type hitter --max-players 30 --epochs 3 --through-season 2025
```

전체 선수로 학습·평가하고 서비스 모델로 적용:

```sh
docker compose exec backend python -m app.ml.train --type both --through-season 2025 --validation-season 2024 --test-season 2025 --activate
```

기존 버전을 재학습 없이 적용하거나 이전 버전으로 복귀:

```sh
docker compose exec backend python -m app.ml.train --type hitter --activate-version VERSION
```

로컬에서는 `backend`를 작업 디렉터리로 하고, 의존성이 설치된 Python으로
`python -m app.ml.train ...`을 실행합니다. 연결 설정은 `DATABASE_URL` 또는 `DB_*`입니다.
선수 표본은 `--seed`로 고정하고, 보고서에 실제 선수 ID와 데이터 지문도 남깁니다.

새 데이터가 들어오면 같은 학습 명령을 다시 실행해 새 버전을 만들고 결과를 확인한 뒤
활성화합니다. 기본은 처음부터 재학습이며, 자동 예약 실행은 설정하지 않았습니다.
독립 테스트를 유지하기 위해 저장 모델도 학습 구간으로만 학습된 모델입니다.
평가 후 검증/테스트까지 포함하는 서비스용 최종 재학습은 이 명령이 수행하지 않습니다.

## 저장 내용

기본 위치는 `backend/models/lstm`이며 Git에서 제외됩니다. `ML_MODEL_DIR` 환경변수나
학습 명령의 `--model-dir`로 바꿀 수 있습니다. API와 학습 명령은 같은 경로를 사용해야 합니다.

```text
models/lstm/hitter/
  current.json                  # 활성 버전 이름
  YYYYMMDDTHHMMSS-xxxxxxxx/
    model.keras                 # 모델 구조·가중치·옵티마이저 상태
    scalers.json                # 입력·출력 스케일러의 수치 상태
    report.json                 # 분리 연도·MAE·RMSE·학습 이력·설정·버전·파일 지문
```

타자·투수는 각각 저장합니다. 선수마다 모델 파일을 만들거나 전체 원본 DB를 복제하지
않습니다. 학습 이력의 `mae/rmse/val_mae/val_rmse`는 정규화 단위이고, 보고서의
`evaluation.metrics`(테스트)와 `validation_metrics`는 지표별 **원래 단위**입니다.

보고서에는 `preprocessing_version=2`를 기록합니다. 이전 전처리로 학습한 모델은
타자 입력 차원이 같더라도 사용할 수 없으며, 새 전처리로 재학습 후 활성화해야 합니다.
투수 API의 예측 지표도 `so_per_g`에서 `k9`로 바뀌었고 예측 화면에 K/9로 표시합니다.

저장 완료 후에만 작은 활성 버전 포인터를 원자적으로 교체합니다. 실패한 저장은 기존
활성 버전에 영향을 주지 않습니다. API는 다음 요청에서 버전 변경을 확인해 새 모델을
로드하므로 재학습·서비스 재시작이 필요하지 않습니다. 파일이 없거나 로드가 실패하면
`model_status`로 사유를 반환하고 가중평균으로 대체합니다.

버전은 자동 삭제하지 않습니다. 실험을 많이 하면 버전 수에 비례해 용량이 늘어나므로
필요한 결과를 보관한 뒤 사용하지 않는 버전만 별도로 정리하세요.

## 검증

DB가 실행 중이지 않아도 저장소 CSV로 실제 성능을 측정할 수 있습니다. `backend`에서:

```sh
python -m app.ml.benchmark --type both --through-season 2025 --validation-season 2024 --test-season 2025 --epochs 100 --patience 10 --seed 42
```

최대 100 epoch까지 학습하되 **검증 `val_rmse`가 10 epoch 연속 감소하지 않으면**
조기 종료합니다(`min_delta=0`, 같은 값도 개선으로 세지 않음). 종료 후 가장 낮은
검증 RMSE를 기록한 epoch의 가중치를 복원한 뒤 테스트합니다. 테스트 데이터는
조기 종료 판단에 사용하지 않습니다. 보고서에는 `epochs_run`, `best_epoch`,
`stopped_early`와 `training_config.early_stopping`을 기록합니다.

학습·검증·테스트 처리와 모델 구조는 서비스 학습 코드와 같습니다. 테스트 대상과 순서를
고정하고 LSTM, 전년도 성적 유지, 현재 가중평균 대체 예측의 MAE·RMSE를 비교합니다.
`models/benchmarks/<실행 버전>/summary.md`, `summary.json`과 모델별
`test_predictions.csv`에 개별 선수의 정답·예측값을 저장합니다. 원본 CSV의 경로·SHA256도
보관하며 이 명령은 서비스 모델을 활성화하지 않습니다. `--csv-dir`로 입력 CSV 폴더를,
`--output-dir`로 보고서 루트를 지정할 수 있습니다. 기본 연도는 첫 실험에 맞춘 2024/2025이므로
다른 시즌을 평가할 때는 세 연도 옵션을 명시적으로 바꾸세요.

### 최근 5시즌 입력 비교 실험

서비스 기본 입력은 3시즌으로 유지합니다. 다음 명령은 5시즌 입력 모델을 별도로 학습하고,
기존 3시즌 실행의 `test_predictions.csv`에서 공통 선수만 골라 두 모델의 오차를 재계산합니다.
`--compare-run`에는 기존 실행의 `summary.json`이 있는 폴더를 지정하세요.

```sh
python -m app.ml.benchmark --type both --lookback 5 --epochs 100 --patience 10 --seed 42 --through-season 2025 --validation-season 2024 --test-season 2025 --compare-run models/benchmarks/<기존_3시즌_실행>
```

`summary.md`는 해당 모델 전체 테스트 표본, `comparison.md`와 `comparison.json`은
공통 테스트 선수에 대한 3시즌·5시즌 비교입니다. 학습·검증 표본은 입력 길이에 따라 달라집니다.
가중평균 기준 모델은 5시즌 실험에서도 기존 최근 3시즌만 사용합니다. 5시즌 결과는 실험
전용으로 저장되며 현재 API의 입력 규격이 다르므로 서비스 활성화를 차단합니다.

### 출전량 입력과 단층 LSTM 비교

```sh
python -m app.ml.ablation --type both --epochs 100 --patience 10 --seed 42 --through-season 2025 --validation-season 2024 --test-season 2025
```

타자는 기존 입력/출전량 입력 × 기존 64→32/단층 32/단층 16의 6개 조합,
투수는 기존 입력을 유지한 구조 3개를 비교합니다. 출전량 입력은 PA·AB·G와 각 변화량을
추가한 14개입니다. 변화량은 입력 3시즌 안에서만 계산하며 첫 입력은 0으로 둡니다.
나이는 현재 프로필에 없는 은퇴 선수 등을 제외하는 편향을 피하기 위해 사용하지 않고
확보 범위만 기록합니다. 모든 조합의 정답·스케일러 기준·테스트 선수 일치를 검사합니다.

`models/ablations/<실행>/summary.md` 및 `summary.json`에 검증·테스트 점수, 모델 크기,
종료/최적 epoch를 저장합니다. 조합 선택은 **정규화 검증 RMSE**만 사용합니다.
2025년 점수는 이미 확인한 과거 연도의 참고 테스트이며 새로운 독립 최종 평가가 아닙니다.
이 실험은 기본 입력·모델 구조를 바꾸지 않고, 저장된 실험 모델의 서비스 활성화도 차단합니다.
다른 회귀 모델·손실 함수·학습률 조정은 이 명령에서 실험하지 않습니다.

`backend`에서:

```sh
python -m unittest discover -s tests -v
```

실제 TensorFlow로 작은 합성 데이터의 학습·저장·재로딩까지 확인하려면 환경변수
`RUN_LSTM_SMOKE=1`을 설정한 뒤 같은 명령을 실행합니다. 이 테스트는 실제 DB에
연결하거나 서비스 모델을 활성화하지 않으며 임시 경로에만 저장합니다.
